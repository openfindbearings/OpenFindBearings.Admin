## 1. 概述

Admin 项目通过标准 JWT Bearer 认证接入 Identity 认证中心，实现用户登录与后台操作。登录成功后，面板角色与权限由 API RBAC 托管，Admin 仅将登录时拉取的角色/权限写入 Cookie 声明用于界面与控制器判权。

### 1.1 认证架构

```
用户浏览器
    |
    v
Admin 项目（Cookie 会话 + 令牌注入）
    |
    +-- 未登录 -> 跳转 Identity /connect/authorize -> 登录 -> 回调拿 code -> 换 JWT
    +-- 已登录 -> Cookie 验证通过 -> panel_role / permission claim 判权
    |
    v
API 项目（JWT 验证 + 权限校验）
    |
    +-- 验证 JWT 有效性 -> 校验具体权限
    +-- GET /api/me/permissions 提供当前用户角色与权限清单
```

### 1.2 技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 认证方案 | JWT Bearer + Cookie | 标准 JWT 验证，不用 OpenIddict 客户端包 |
| 认证中心 | Identity（OpenIddict） | OIDC 授权码流程 |
| 会话管理 | Cookie | 存储访问令牌与刷新令牌声明 |
| 权限控制 | 面板角色 + API 托管权限目录 | 登录时拉取写入 Cookie 声明，无本地库 |

## 2. OIDC 认证流程

### 2.1 授权码流程

```
1. 用户访问 Admin 任意页面
2. [Authorize] 未认证 -> 401 -> 跳转 /Account/Login
3. /Account/Login -> LoginAction 构造 OIDC 请求 -> 跳转 Identity /connect/authorize
   （参数：response_type=code、client_id、redirect_uri、scope、state、realm、device_id）
4. Identity 检查登录状态 -> 未登录 -> 登录页
5. 用户登录 -> Identity 授予 code -> 回调 Admin /callback?code=xxx&state=xxx
6. Admin 用 code + Basic(client_id:client_secret) POST 到 Identity /connect/token
7. 拿到 access_token + refresh_token，向 API GET /api/me/permissions 拉角色与权限
8. 角色与面板角色全集无交集则拒登并提示；否则写 Cookie 声明 -> 跳转原始请求页面
```

`device_id` 在首次登录时生成并写入 Cookie（已存在则复用），随授权请求与刷新请求上送，用于 Identity 侧的设备绑定。

### 2.2 Token 刷新（无感）

```
1. 令牌临期或后端返回 401
2. BearerTokenHandler 通过 AdminTokenService 取用新鲜令牌
3. AdminTokenService 用 refresh_token POST 到 Identity /connect/token
4. 获取新 access_token + refresh_token
5. 写进程缓存（按 device_id 键）并回写 Cookie -> 本次请求用新令牌
6. refresh_token 也失效 -> 取用失败 -> 重新登录
```

缓存与并发：`AdminTokenService` 为 Scoped，但令牌缓存与单飞锁是进程级静态结构，按 `device_id` 为键。同一浏览器并发请求时，先刷成功者写入缓存，其余请求在锁内 double-check 命中缓存即复用，避免重复消费滚动 refresh_token。单副本部署为前提。

### 2.3 登出流程

```
1. 用户点击退出
2. /Account/Logout -> 清除本地 Cookie，并使该 device_id / userId 的进程级令牌缓存失效
3. 跳转 Identity /connect/logout?post_logout_redirect_uri=<host>/signout-callback-oidc
4. Identity 清除会话 -> 重定向 Admin /signout-callback-oidc
5. Admin 重定向到登录页
```

## 3. 端口与回调配置

### 3.1 开发环境

| 项目 | 端口 | URL |
|------|------|-----|
| Identity | HTTPS 7201 | `https://localhost:7201` |
| Admin | HTTPS 7167 | `https://localhost:7167` |
| API | HTTPS 7183 | `https://localhost:7183` |

### 3.2 回调地址

| 配置项 | 值 |
|--------|-----|
| Admin 授权回调 | `/callback`（`[HttpGet("~/callback")]`） |
| Identity redirect_uri | `https://localhost:7167/callback` |
| Admin 登出回调 | `/signout-callback-oidc`（`[HttpGet("~/signout-callback-oidc")]`） |
| 登出 post_logout_redirect_uri | `https://<admin-host>/signout-callback-oidc` |
| 修改密码回跳 | `https://<admin-host>/` |

### 3.3 生产环境回调地址维护

OpenIddict 的 redirect_uri 存储于 Identity 侧的应用注册中。域名变更时须在 Identity 的 OpenIddict 应用配置中更新 redirect_uris；同一 ClientId 可注册多个 redirect_uri 支持多环境共存。具体维护方式以 Identity 项目为准。

## 4. NuGet 包

| 包名 | 用途 |
|------|------|
| `Microsoft.AspNetCore.Authentication.JwtBearer`（10.0.13） | JWT Bearer 认证 |

## 5. 认证与授权中间件配置

```csharp
// Program.cs（节选）
// 动态策略提供器：Panel:key 形式策略按需生成；处理器读 Cookie 中的 permission claim
builder.Services.AddAuthorization();
builder.Services.AddSingleton<IAuthorizationPolicyProvider, PanelPolicyProvider>();
builder.Services.AddSingleton<IAuthorizationHandler, PanelPermissionHandler>();
builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.LoginPath = "/Account/Login";
        options.LogoutPath = "/Account/Logout";
        options.ExpireTimeSpan = TimeSpan.FromHours(8);
        options.SlidingExpiration = true;
        // 30 分钟复核：重拉 API /api/me/permissions，角色被收回则 RejectPrincipal，
        // 否则替换 permission/panel_role claim 续期；API 不可达时放行，下轮重试
        options.Events.OnValidatePrincipal = /* ... */;
    })
    .AddJwtBearer(options =>
    {
        // 从配置读取，不硬编码
        options.Authority = builder.Configuration["Identity:Authority"];
        options.Audience = builder.Configuration["Identity:ClientId"];
        options.RequireHttpsMetadata = false;
    });
```

> 注：文档历史版本曾记载硬编码 `Authority` 与 `SaveTokens = true`，实际代码从 Configuration 读取且未启用 SaveTokens（Admin 经 AdminTokenService 手动管理刷新与 Cookie 回写）。

### 5.1 令牌注入与后端异常处理（BearerTokenHandler）

- 对 `/connect/*`（code 换 token、revocation 走 Basic/表单客户端认证）与 `/health*`（匿名）**跳过**注入，避免冲掉 Callback 设置的 Basic 认证。
- 其余请求注入当前用户的有效访问令牌（临期自动刷新）。
- 后端抛出 `HttpRequestException` 时，合成 `502 Bad Gateway` 与 JSON 体 `{ success:false, message:"后端服务暂时不可用" }`，供上游页面优雅降级。

## 7. 用户管理（调 Identity API 与 API）

### 7.1 数据流

```
Admin UsersController
    |
    +-- 账号侧（Identity）：/api/account/admin/users*
    |     GET     /api/account/admin/users?page=&pageSize=        用户列表
    |     POST    /api/account/admin/users                        创建账号
    |     PATCH   /api/account/admin/users/{id}/status            启用/禁用
    |     POST    /api/account/admin/users/{id}/unlock            解锁账户
    |     POST    /api/account/admin/users/{id}/reset-to-default  重置密码
    |     POST    /api/account/admin/users/{id}/restore           恢复
    |     DELETE  /api/account/admin/users/{id}/permanent         物理删除（仅已软删）
    |     DELETE  /api/account/admin/users/{id}                   软删除
    |
    +-- 平台角色侧（API RBAC）：/api/admin/users*
          GET     /api/admin/users/platform-roles                 sub -> roles 批量字典
          GET     /api/admin/users/by-auth/{sub}/roles            单用户现有平台角色
          POST    /api/admin/users/provision                      幂等挂载全部勾选角色
          DELETE  /api/admin/users/by-auth/{sub}/roles/{role}     移除单个角色
```

浏览器不持有 API 令牌，故平台角色读取/写入均由本控制器以命名 HttpClient 代理，键为 Identity 的 `sub`。

> 注：文档历史版本曾记载本地 `admin_user_roles` 表与 `POST .../toggle-status`，实际不存在本地表，用户状态端点实际为 `PATCH .../status`。

### 7.2 页面功能

| 功能 | 说明 |
|------|------|
| 用户列表 | 搜索 + 分页 + 状态筛选 + 平台角色列（经 API 批量字典合并） |
| 重置密码 | 重置为默认密码 |
| 启用/禁用 | 切换用户状态（status） |
| 解锁 | 解除账户锁定（unlock） |
| 分配平台角色 | 选择 API 平台角色（Admin/Operator/Auditor 等），差集写入；含自锁守卫（不能移除自己的 Admin） |
| 删除/恢复 | 软删除 + 恢复 + 物理删除（仅已软删用户） |

## 8. 角色管理（面板角色 + API 托管权限目录）

### 8.1 数据来源

Admin 无本地角色权限表。角色与其权限的读写全部代理 API RBAC：

| 功能 | API 端点 |
|------|----------|
| 角色列表 | `GET /api/admin/roles`、`GET /api/admin/roles/all` |
| 角色权限查询 | `GET /api/admin/roles/{id}/permissions` |
| 新建角色 | `POST /api/admin/roles` |
| 删除角色 | `DELETE /api/admin/roles/{id}` |
| 分配角色权限 | `POST /api/admin/roles/{id}/permissions` |

`RoleController` 负责上述代理，`PermissionController` 只读展示权限目录。

### 8.2 页面功能

| 功能 | 说明 |
|------|------|
| 角色列表 | 分页展示角色（英文机器标识 + 中文显示名） |
| 新建角色 | 输入角色名称 |
| 删除角色 | 确认后经 API 删除 |
| 分配权限 | 勾选权限目录中的权限点，经 API 保存 |

### 8.3 预置角色

预置角色由 API 种子数据定义（数量随 API 权限目录而变，以 API 为准）：

| 角色 | 说明 | 权限点 |
|------|------|--------|
| Admin | 平台管理员 | 全部 34 个权限键 |
| Operator | 平台操作员 | 20 个（仪表盘、数据管理 view/create/edit、替代关系查看与维护、审核组、寻货治理、用户封禁） |
| Auditor | 平台审计员 | 12 个（各 view 键 + 替代关系查看 + 纠错审核 + 审计日志） |

> 注：替代关系（替代品）为平台主数据，其权限键自 v1.2.3 起独立为 `interchange.view`/`interchange.manage`。「替代品管理」页由 `interchange.view` 进入，页内新建/编辑/删除按钮由 `interchange.manage` 控制。

## 9. 权限管理（API 托管，只读）

### 9.1 权限目录

| 商家管理 | `merchant.view` `merchant.manage` `merchant.verify` `merchant.detach` |

### 9.2 页面功能

只读展示权限键表格（按分组），供管理员了解系统权限体系。

## 10. 侧边栏结构

```
认证管理
+-- 用户管理    (Users/Index)        user.view
+-- 角色管理    (Role/Index)         role.manage
```

认证管理分组在组内任一权限命中时显示；角色管理与权限管理项的显隐分别由 `role.manage`、`permission.view` 决定。

## 11. 与 Identity、API 的边界

| 操作 | Admin 处理 | Identity / API 处理 |
|------|-----------|---------------------|
| 用户认证 | Cookie 存储令牌声明 | Identity 经 OIDC 签发 token |
| 用户账号 CRUD | HTTP 调用 Identity API | Identity 实际数据库操作 |
| 面板角色与权限 | 登录时拉取写入 Cookie claim | API RBAC 表为唯一事实源 |
| 权限校验 | Cookie claim 判权（无跨服务调用） | API 端点侧二次校验 |
| 租户筛选 | 传 realm 参数 | Identity 数据库过滤 |
